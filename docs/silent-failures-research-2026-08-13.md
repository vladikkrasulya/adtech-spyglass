# Тихі поломки в програматику — дослідницький зріз (2026-08-13)

> **Historical snapshot (2026-08-13).** This research preserves the measurements and conclusions
> available at that date; the catalogue entries it lists are hypotheses that each still need their
> own verification. Use the [platform baseline](../specs/000-platform-baseline/plan.md) for current
> behavior and the [Spec Kit roadmap](../specs/ROADMAP.md) for active work.

> **Статус: дослідження, не заплановані роботи.** Цей документ фіксує, що встановлено, що
> перевірено власними замірами, а що лишається гіпотезою. Перетворення будь-якої частини
> на роботу проходить через `speckit.assess` і власний feature package, за
> [ROADMAP](../specs/ROADMAP.md).

## 1. Що вирішено

**Позиціонування: глибина на одній транзакції, не ширина.**

ortbtools приймає один evidence bundle (запит, відповідь, VAST-тег) і пояснює весь шлях від
байтів до результату. Не ще один schema checker.

Підстава: два незалежні дослідження, проведені наосліп і паралельно, дійшли того самого
висновку з різних боків, плюс власні заміри. Синтаксична валідація вже commoditized —
RTBlint, інструменти IAB, бібліотеки, вендорські портали перевіряють окремі зрізи. Найдорожчі
поломки виникають **між шарами**: debug→transport, version→transform, request→response,
privacy→redaction, VMAP→VAST→player.

Що переконало б у зворотному: якби більшість інцидентів вирішувалась inventory-wide аудитом
до аукціону, а не трасуванням конкретної транзакції.

## 2. Обмеження архітектури

> Будь-який розбір — це projection із втратами. Дублікати ключів, int64, макроси, побиті біти
> згоди зникають **у момент парсингу**. Інспектор, який працює з розпарсеним об'єктом, за
> визначенням не може їх побачити.

Наслідок: сирі байти зберігаються незмінними, розібране подання є похідним, кожне
перетворення логується. Це не пункт беклогу — це умова, без якої частина знахідок нижче
недосяжна в принципі.

Той самий висновок незалежно отриманий у [специфікації URL-входу](./url-input-spec-2026-08-13.md) для поля `_raw`:
`_canonical.js:45` обіцяє «Original query params verbatim», а `_authenticated-json-feed.js:30`
будує його з `searchParams`, тобто вже після втрат.

## 3. Перевірено власними замірами

Node 22.23.2 (ada) · Chrome 151 (GURL) · Firefox 140.13.0esr (rust-url) · Python 3.13.5 ·
`@iabtcf/core`. Розбіжностей між URL-рушіями не виявлено на жодному випадку.

### 3.1. Дублікати ключів JSON зникають до валідації

```
байти:  {"id":"A", … ,"id":"B","bidfloor":1.5,"bidfloor":9.99}
parse:  id="B"   bidfloor=9.99          ← Node і Python однаково, мовчки
```

RFC 8259 §4 поведінку не визначає — інший приймач може взяти перше значення. `bidfloor` 1.5
проти 9.99 це гроші. Після `JSON.parse` неоднозначність не відновлюється.

### 3.2. int64 псується залежно від мови приймача

```
9007199254740993      → 9007199254740992      Node, тихо
1234567890123456789   → 1234567890123456800   Node, тихо
обидва                → без змін               Python (big int)
```

Ті самі байти дають різні ID. `Number.MAX_SAFE_INTEGER` = 9007199254740991.

### 3.3. Одрук у полі виглядає як нешкідливе майбутнє поле

`protcols` замість `protocols`, `bidfloorcurr` замість `bidfloorcur`. Правило
forward-compatibility велить ігнорувати невідомі поля, тому effective value стає `undefined`
без жодного сигналу.

### 3.4. `searchParams` знищує нерозгорнуті макроси

```
?cb=%%CACHEBUSTER%%   →   searchParams.get("cb") = "%<U+FFFD>CHEBUSTER%%"
?cu=%%CLICK_URL%%     →   ціле
```

Механізм: другий `%` разом із першими двома літерами імені утворює percent-escape, якщо ці
літери — валідна hex-пара. `CA` → 0xCA → невалідний UTF-8 → U+FFFD. З 25 перевірених імен
гине 10. `u.href` при цьому виглядає цілим; помилки не кидається.

**Застереження щодо походження:** тестований корпус імен узято зі списку, наданого без джерел.
Офіційний реєстр GAM використовує, зокрема, `ADUNIT`, а не `AD_UNIT`. Правило від цього не
змінюється (`AD` — hex у обох варіантах), але звірка з офіційним реєстром лишається
невиконаною.

### 3.5. Побитий TC-рядок мовчки декодується в іншу згоду

`@iabtcf/core`, пошкодження по чотири символи у різних вікнах валідного рядка:

```
позиція 16  →  decode OK   consentLanguage: "EN" → "ZZ"
позиція 20  →  decode OK   policyVersion: 2 → 25
                           specialFeatureOptins: [] → [1,4]
позиція 24  →  decode OK   purposeConsents: [1,2] → [1,4,6,7,10,12,13,16]
позиція 28  →  decode OK   purposeLegitimateInterests: [] → [1,4,6,7,10,12,13,16]
```

Жодного винятку. Бібліотека вигадує згоду на цілі, яких користувач не давав, і вмикає
`specialFeatureOptins` — точну геолокацію і сканування пристрою.

Усічення й побитий base64 навпаки падають одразу на `decode()`. Тобто гіпотеза «пройде на
заголовку, вибухне пізніше при доступі до вендора» в Node-реалізації **не підтвердилась** —
реальна поведінка інша й гірша.

**Не перевірено:** `iabtcf-java`. Якщо Java падає там, де Node мовчки вигадує дані, це саме по
собі знахідка: дві офіційні бібліотеки IAB розходяться в поведінці на однаковому вході.

### 3.6. Що `new URL()` робить і чого не робить

Нормалізує сам (дублювати не треба): регістр схеми й хоста, дефолтні порти `:80`/`:443`,
`../`, крайні пробіли, внутрішні TAB/LF/CR, пробіл → `%20`.

**Не чіпає:** `U+200B`, `U+00A0`, `U+00AD`, `U+FEFF`, `U+2028`, `U+0000` — усі проходять
наскрізь у percent-кодованому вигляді.

Кидає помилку: без схеми, scheme-relative, будь-які обгортки (`"`, `'`, `` ` ``, `<>`, `()`,
markdown).

Приймає без помилки, тлумачить не як людина: `adserver:8080/feed` → `protocol="adserver:"`.
Дефіс у схемі легальний, тож `ad-server:8080/feed` теж — а це типове ім'я Docker-хоста.
Підкреслення й цифра на початку рятують (`ad_server:`, `127.0.0.1:` кидають помилку).
`javascript:alert(1)` парситься без заперечень — заборонені схеми потребують явного списку.

## 4. Каталог гіпотез

Два дослідження дали 56 позицій. Перевірено п'ять. **Решта — гіпотези з походженням, не
встановлені факти.**

| Джерело       | Позицій | Дисципліна доказів                                                                                                                                                                                                                           |
| ------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Дослідження A | 8       | колонка «джерело» порожня в усіх рядках; посилання звалені списком у кінці; кілька позицій внутрішньо суперечливі                                                                                                                            |
| Дослідження B | 48      | тип джерела на кожному рядку (`[S]` спека, `[C]` запінений код, `[V]` вендор, `[I]` issue, `[U]` наш замір); 14 запінених комітів; окремі розділи «що найслабше» і «що не стверджується»; відмова вигадати рядок для неіснуючого інструмента |

Найвище оцінені неперевірені позиції, варті перевірки насамперед:

- **debug-режим змінює саму систему** — `pbjs_debug` вимикає gzip; PBS `test:1` може змінити
  склад учасників аукціону. Налагодження здатне сховати transport-баг або створити інший аукціон
- **PBS не викликає біддера через effective tmax** — виглядає як його no-bid, хоча запиту не було
- **EIDs у двох домівках** — PBS відкидає legacy `user.ext.eids` за наявності `user.eids`,
  PBJS натомість зливає. Один capture дає різні outbound ID sets
- **2.5↔2.6 relocation** — GDPR, consent, us_privacy, schain, EIDs змінили home; приймач читає
  лише очікуваний шлях
- **`&amp;` у CDATA** — у VAST це literal text, не entity; XML-валідатор зелений, HTTP-запит інший
- **schain `sid` як Integer замість String** — строгі protobuf-парсери дропають вузол або запит

## 5. Перший зріз до реалізації

П'ять перевірених знахідок — це **один механізм**, не п'ять фіч: тримати сире, порівнювати з
розібраним, показувати розбіжність.

| Детектор                                            | Знахідка | Що потрібно                                      |
| --------------------------------------------------- | -------- | ------------------------------------------------ |
| скан дублікатів ключів по байтах, до `JSON.parse`   | 3.1      | токенізатор, не `JSON.parse`                     |
| небезпечні цілочисельні токени > 2⁵³−1              | 3.2      | лексичний скан сирих байтів                      |
| невідомі поля + підказка найближчого імені          | 3.3      | реєстр відомих полів на версію                   |
| сирий query, детектор побитих макросів через U+FFFD | 3.4      | розбір `u.search` без декодування                |
| структурна санітарія TC-рядка                       | 3.5      | діапазони `policyVersion`, ISO 639-1, реєстр CMP |

Найсильніша окрема перевірка для TC-рядка — round-trip: розкодувати, закодувати назад, звірити
з оригіналом. Вимагає завантаження GVL, тобто мережевої залежності.

## 7. Метод роботи з дослідженнями

Зовнішні агенти працюють **тільки з текстом**, без доступу до сервера й репозиторію. Вони дають
первинні джерела й аргументи; усі заміри роблю я.

Правило в кожен бриф: «Таблиць із заміряними результатами не наводь. Якщо для відповіді потрібен
замір — опиши точний тест: входи, рушій, що дивитись. Прогін мій.»

Підстава: доступ до середовища не покращив результат, він створив можливість підробити
результат. Агент, який не може зміряти, дописує правдоподібну таблицю замість «не міряно». Той,
що працював лише з текстом і замовляв тести, дав найякісніший документ.

Кілька агентів на одному питанні запускати наосліп і паралельно, не показуючи одному результат
іншого. Давати їм факти, не свої висновки. Де вони розійшлись — випадок вважати невирішеним.

## 8. Як це входить у роботу

Ніяк, поки не пройде гейт. За [ROADMAP](../specs/ROADMAP.md), P3 «Product features» вимагає
`assess one bounded problem before opening a feature package`. Найменша осмислена bounded
problem тут — зріз із §5: один механізм, п'ять детекторів, усі підперті власними замірами.

Суміжна готова робота: [специфікація обробки вставленого URL](./url-input-spec-2026-08-13.md) — рішення до реалізації,
виведені з тих самих замірів, з трьома підтвердженими дефектами в наявному коді
(`_raw` порушує контракт; `decodeRequest` повертає `null` на дві різні події; хвостова
пунктуація приймається мовчки).
