### T001 — does the gate actually bite?

The seal test is a characterisation test, so it is green the moment it is written — which proves
nothing on its own. What it is worth is whether it fails when the thing it guards changes. Measured by
editing the policy in the working tree and running it, in both directions:

```
img-src data: blob:          → 6 tests, 6 pass       (as shipped)
img-src data: blob: https:   → 6 tests, 4 pass, 2 fail   (widened)
img-src blob:                → 6 tests, 4 pass, 2 fail   (narrowed)
img-src data: blob:          → 6 tests, 6 pass       (restored, `git diff --stat` clean of the edit)
```

Stated plainly: the order of work was module-then-test for the classifier, not test-then-module. The
classifier existed before `tests/creative-preview-classify.test.js` ran for the first time, and the
first run was 20/23 — three genuine failures, all in the test's own loader and in the VAST fallback
regex, not in the classification table. That is not TDD and the phase heading says "tests first", so
the discrepancy is recorded rather than papered over.

### T028 — a gate that only bites after `git add`

`npm run ci` was green three times before the commit and red on the first `git push`, from the
identical tree. `tests/brand-guard.test.js` walks `git ls-files`, so while this package was untracked
it was outside the guard's scope entirely; committing brought it in, and one line in
`checklists/requirements.md` quoting the retired brand name failed it.

Recorded because the lesson is about ordering, not about the name: a gate scoped to tracked files
cannot be trusted until the files are staged. Running `npm run ci` before `git add` proves less than
it appears to. The `pre-push` hook is what caught it — the same `npm run ci`, run at the only
moment when the tree and the index agree.

Fixed by rewording the note rather than adding the file to `FILE_ALLOWLIST`: that list is for
historical documents that must quote the old name to be useful, and this note is not one.
